## 从反复推理到可复用的引擎

一个 Agent 可能多次执行同一类任务。每次输入不同，但背后的结构往往相似：查找信息、理解信息、检查约束、选择动作，然后观察结果。细节在变化，很多计算却在重复。

这些执行经验，能否成为构建一个新执行引擎的材料？

我设想，让 LLM 阅读任务、示例和执行轨迹，生成一个包含两类组件的程序：能够明确表达的部分写成确定性代码，难以写成规则的决策则留给可学习的模块。

最初，这些困难的部分可以由 LLM 自己完成。随着经验积累，小型的任务专用网络逐渐接管其中一些计算。引擎在学习过程中依然可以使用；如果最初的任务分解不合理，整个结构也可以改变。

**我想研究的是：Agent 如何把经验变成一种计算结构，使执行越来越便宜，同时保留处理例外的能力？**

这是一种待验证的架构设想，并不意味着完整系统已经实现。

## 编译执行结构，留下明确的空位

以一个范围受限的日程安排任务为例。系统读取请求、检索可用时间、检查硬约束、给候选方案排序，最后提出安排。

日期计算、空闲时间检查和数据库更新，通常可以写成普通代码。但理解“上午尽量不要排得太满”，或者权衡多个软偏好，可能需要一个学习型决策模块。

编译器可以生成程序骨架，并在这些位置留下命名的空位，也就是图中的 holes。每个空位都需要明确的接口约定：接收什么状态、返回什么结果、必须通过哪些检查，以及什么情况下应该放弃作答。例如，一个排序空位可以接收已经符合硬约束的候选日程，返回它们的顺序。硬约束仍由外围程序负责执行。

恢复这种结构，不能只复制某一次成功的工具调用顺序。系统需要从多条轨迹中区分可复用的依赖与分支，以及偶然细节、重试和失败探索。示例可以暴露潜在结构，却不能证明未来所有情况都遵循同一规律。

**一个空位应当对应边界清晰的计算，而它的输入必须包含足够的信息，才能让这项计算被学会。**

## 让每个空位在引擎运行时学习

最初，空位直接调用 LLM。系统记录局部状态、教师提出的答案，以及能够得到的验证结果或后续反馈。这些记录成为小模块的候选训练样本。

“候选”很关键。LLM 的回答只是一个候选标签，不是真值。局部模仿成功，也可能复制教师的错误，或者破坏整个流程的效果。训练数据应当区分：与教师一致、通过局部检查，以及真正完成了任务。

小模块可以先在影子模式下运行，实际答案仍由 LLM 提供。经过独立测试后，系统再允许它处理熟悉的情况，前提是经过校准的门控机制判断风险可接受，而且外围检查通过。遇到不确定或陌生的输入时，继续调用教师；如果两者都无法可靠回答，就应请求澄清。

这个循环在概念上很简单：观察局部状态，在适用时尝试小模块，验证输出，必要时升级处理。新的验证样本用于后续训练和评估。更新线上模块则应当是一个独立且可回退的步骤。

于是，LLM 同时承担三种角色：构建初始引擎、教授局部模块，以及在任务分解失败时修改程序。

## “长出一个小网络”具体意味着什么？

“生长”应当对应可以检验的具体操作。例如，系统选择输入表示，从有限的候选架构中挑选小网络，收集样本，训练、评估，然后把它接入空位的接口。之后，也可以调整容量，或者把一个困难的空位拆成两个更简单的计算。

对于原型，一个分类器或排序网络就足够了。自动发现新架构可以留待后续研究。首先要回答的是：能否识别出稳定的局部问题，并以合理的成本学会它？

如果一个模块持续失败，问题未必是网络太小。可能输入遗漏了必要背景，可能两种看似相似的情况实际需要不同策略，也可能程序在收集证据之前就要求模块作出判断。

这时，LLM 可以重写外围代码，或者修改接口。但这样的修改也会改变学习问题。旧样本可能不再适用，受影响的模块需要重新训练或验证，才能部署。

## 为每一块可复用计算选择实现方式

这引出了更一般的研究问题：哪些重复行为适合成为代码，哪些适合成为学习型计算？

- 精确变换和明确约束，可以优先考虑确定性程序。
- 结构稳定、偶尔出现语义歧义的过程，可以使用代码加 LLM 兜底。
- 重复出现、边界清晰的判断，可以尝试小型专用网络。
- 更广泛的重复能力，可能值得用 LoRA 等适配器，或其他内部学习表示来承载。

这些选项构成一个设计空间，并不是严格的一维阶梯。LoRA 依然依赖宿主模型；latent macro 则需要进一步定义表示方式、调用方式和训练过程。不能因为一个表示紧凑，就默认它的执行成本更低。

选择应取决于覆盖范围、容错要求、数据需求、构建成本和预期复用次数。同一个流程可以同时采用多种实现。当环境改变时，某个组件也可以退回 LLM 兜底。

程序化复用与学习式内化，在这里指向同一个问题：如何把有用的计算保留下来，只是保存它们的表示不同。

## 与 TraceCompiler 的关系

[TraceCompiler](https://arxiv.org/abs/2608.02680) 是一个相关参考。它讨论从 Agent 轨迹中提取以确定性执行为主的工作流、恢复依赖关系，并在语义决策尚未解决的位置保留运行时 LLM 节点。它通过 LLM skill 实现编译器，而不是单独训练一个编译器模型。

我关心的进一步方向，是让这些尚未解决的节点也能学习：为空位配备自己的数据、局部模型、部署门控和修改机制。论文没有证明这种自适应神经模块机制已经实现。它提供了一个有用的比较起点。

## 怎样验证这个想法？

我会从模拟环境开始，选择重复的日程安排或检索排序流程，设置明确约束和可以测量的结果。测试既包含熟悉的情况，也包含新的偏好组合或执行分支。

比较四种系统：通用 LLM Agent、代码加 LLM 空位的引擎、使用固定蒸馏模块的引擎，以及局部模块能够逐渐学习的引擎。沿学习曲线测量完整任务成功率、延迟、教师调用次数和总成本。构建、训练、验证以及失败尝试的费用都需要计入预算。

有价值的测试，还应该在部署后改变语言表达、输入或环境。门控机制能否发现模块已经不可靠？兜底能否维持任务成功率？结构修改能否修复问题，同时保住原来支持的情况？

只有在覆盖范围和质量得到保持时，减少 LLM 调用才有意义。确定性程序可以稳定地犯错，自信的小网络也可能答错。研究目标应当是更好的完整系统。

最让我感兴趣的是，Agent 可以逐渐形成自己持久的工作方式：规则清晰的地方使用显式程序，经验有帮助的地方使用学习模块，仍然不确定的地方保留通用推理。它的执行引擎，也成为它能够研究、改进和检验的对象。
