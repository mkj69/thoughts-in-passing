我越来越在意 Agent 创作中的一个时间差：人还没有想完，Agent 已经开始做了。最初只有一个模糊的方向，几轮对话以后，代码、图表和文档已经堆了起来。它似乎做了很多事，我却未必能回答一个简单的问题：做完以后，这件作品究竟应该是什么样子？

这个时间差会逐渐变成理解上的负担。Agent 必须补上没有说清楚的部分，才能继续执行。它选择了结构，解释了目标，取舍了细节。这些选择未必单独看就有问题，但组合起来，可能把作品带到一个我还没有想过、也没有真正同意的方向。

于是，人的工作从创作变成了追赶。我需要先理解它已经做出的东西，再反推出它替我做了哪些决定，最后才能判断哪些地方需要改。Agent 越能快速生成大量内容，这种负担就越有可能被放大。

我想尝试另一种协作顺序：**先和 Agent 尽快把作品想清楚，让人能够看见完成后的样子，再把大量实现交给它。** 人的关键思考可以先告一段落，作品则在之后继续完成。

“Begin with the End in Mind”很适合描述这个方向。这是 Stephen R. Covey《高效能人士的七个习惯》中已有的表达，FranklinCovey 对它的解释包括先明确期望的终点，再据此行动。我想把这个原则放进人与 Agent 的创作关系里，讨论它对交互方式的具体要求。[Habit 2: Begin With the End in Mind](https://www.franklincovey.com/courses/the-7-habits/habit-2/)

目前的困难经常同时出现在几个地方。一个项目被切进多个对话，理由和决定散落在不同消息里。每次回来，都要重新找回“我们到底在做什么”。聊天记录保存了说过的话，却未必保存了一个清楚的、仍然有效的作品状态。

等待也没有真正释放注意力。Agent 在运行，我暂时不用操作，但任务还悬在那里：它是不是理解了？等会儿会不会回来问一个小问题？现在可以去做别的事了吗？这种等待可能只占几分钟，却让人很难离开当前任务。

结果出现以后，审核又成为另一种困难。如果我事先没有形成完成状态的认识，就只能临时建立标准，再用这个标准检查一个已经很复杂的产物。审核因此同时承担了理解、设计和验收。一个“看起来不错”的结果，很容易在这种混合判断里获得过早的认可。

这些循环还会打断创作的连续性。刚刚进入整体构思，就被一个文件名或局部实现问题拉走；好不容易想清楚一部分，又要等待下一轮输出。思考被拆成许多短促的反应，人很难保持对整件作品的把握。

![当前协作的常见循环：模糊意图进入执行，未表达的决定藏进产物，人在审核时重新理解并修改，随后再次等待。](assets/images/begin-with-the-end-in-mind/late-decisions-zh.svg)

*图一。尚未完成的思考进入了执行，后来又以审核和返工的形式回到人这里。这是一个概念示意，并非对所有 Agent 系统的统计描述。*

我希望把人的参与集中到一段更连续的过程里。在这段时间内，Agent 快速提出问题，快速展示不同选择会造成的影响，人则持续判断、修改和理解。执行的节奏可以由资源与交付时间决定，构思的节奏则应当尽量跟得上人的思路。

最合适的共同对象，可能是一份完整但粗糙的作品草图。画画时，我们会先知道哪里放主体，哪里留白，光从哪里来。局部还很模糊，整体却已经存在。写文章、做演示、设计实验和构造代码库，都可以有对应的草图。

文章的草图可以让人看到主张如何展开，哪些段落需要证据，读者在哪里可能产生疑问。演示文稿可以先呈现整套页面的节奏，每一页承担什么作用。代码库则可以先呈现关键行为、模块责任、数据流和失败时的处理方式，再按需要深入到接口和实现结构。

草图有价值，是因为它给尚未想清楚的部分一个位置。人可以指着整件作品说：“这里我还不知道应该是什么。”Agent 也能据此发现，下一个值得讨论的问题在哪里。所有决定都回到同一个对象里，作品随着理解一起变得清楚。

这要求 Agent 更主动地参与构思。当它发现一个歧义足以改变结果时，应该把这个歧义变成人能够判断的对照。问题本身还不够，最好让人同时看见不同答案会带来什么。

比如，我说要做一个实验结果分享功能。Agent 可以先展示：一种分享保留发送时的版本，另一种分享持续显示最新结果。它再演示新增结果以后，读者分别会看到什么。这样，“分享”这个词里尚未决定的含义，就变成了可以直接判断的行为。

选择确定以后，预览、数据结构和验收方式需要一起改变。保留版本意味着相关图表和下载数据都应当指向同一份记录；持续更新则需要说明更新何时对读者可见。人刚刚理解的行为，必须继续约束后面的实现。

这个局部问题也应当放在整个作品里理解。它影响读者如何引用结果、如何复现实验，以及报告里哪些描述仍然成立。只给两个孤立的按钮，仍然会把人留在碎片里。Agent 需要展示这个决定如何改变整体。

![以终为始的协作：从粗略的整件作品出发，反复提出关键问题并展示选择的影响，形成共享的完成状态，再交给 Agent 执行和验证。](assets/images/begin-with-the-end-in-mind/shared-outcome-zh.svg)

*图二。预览参与思考，也承接思考的结果。它与实现、验收保持对应，才能让交接具有实际含义。*

实验尤其能说明这个想法的边界。我们可以提前知道最终报告要回答什么问题、主图的横纵轴是什么、哪些方法放在一起比较、需要哪些对照，以及什么证据足以支持怎样的结论。但曲线实际长什么样，必须由实验决定。

例如，我们想判断一种新推理方法是否值得额外成本。草图可以先展示质量与资源的关系，再展示不同任务中的收益和退步。随后，人和 Agent 一起讨论：比较是否公平，平均提升能否掩盖某一类任务的退步，没有明显优势时应该怎样报告。还可以用明确标注的假设结果，预演几种可能的结论。

在这里，“提前知道做完是什么样子”包含的是报告的结构、证据的组织和解释规则。它也包含对未知部分的清楚认识。实验最后没有成功，作品仍然可以按约定完成；一张预览中的漂亮曲线，不能成为执行必须实现的结果。

同样，代码草图可以深入到很具体的结构，而不必提前写完每一行代码。如果一个决定会影响外部行为、成本、可维护性或验收，它值得被显式解决。已经有清楚约束、能够交给 Agent 自行判断的实现细节，则可以留给执行。决定哪些内容需要由人理解，本身也是协作的一部分。

我并不认为人的愿望在开始时已经完整地存在，只等 Agent 把它问出来。很多想法是在看到草图、比较两个可能结果时才形成的。因此，好的预览需要足够便宜，让人可以舍弃一个方向，也需要足够具体，让舍弃或保留有实际依据。

这会带来两个不同的完成时刻。第一个时刻，人已经理解要做出的作品，做完了关键取舍，也知道哪些事情仍然未知、遇到它们时如何处理。第二个时刻，Agent 完成实现，并提供证据说明产物符合约定。两个时刻之间可以相隔很久。

![两条完成线：人的集中构思先达到可以交接的状态，Agent 的执行随后继续，作品在验证以后完成。新的事实只重新打开受影响的决定。](assets/images/begin-with-the-end-in-mind/two-finish-lines-zh.svg)

*图三。希望缩短的是人必须持续挂念任务的时间。图中的间隔没有量化含义；这个收益仍需实际检验。*

“人可以离开”在这里意味着，任务暂时不再需要人的持续关注。它不等于取消验收，也不保证以后永远没有新问题。人离开时，应当知道交付物是什么、执行受哪些资源约束，以及什么情况值得重新打断自己。

如果一个小规模试跑发现原方案超出预算，系统应该明确指出，哪一部分证据和哪一个结论受到影响。已经确定的目的、表达方式和其他约束继续保留。人可以只重新决定受影响的范围，而不必从头理解整个项目。

这也是我对“先把想推进到终局”的理解：把当下可以解决、又足以改变结果的思考尽量前移，并给无法提前知道的事情安排处理方式。有时必须先写一小段代码或做一次廉价试验，才能继续思考。这些动作可以成为构思的工具。没有必要把思考和任何形式的执行机械地隔开。

真正值得改变的是默认交接点。当前的交接经常发生在“我已经描述了一个请求”之后。我希望它发生在“我们已经共同形成了一个足够清楚的完成状态”之后。这个状态可以是可交互的界面、带有证据位置的报告、完整的演示故事板，也可以是能够推演关键行为的代码结构。

因此，项目工作台只是一个可能的容器。把聊天、文件和任务列表放进同一个页面，能够减少寻找信息的成本，但还需要回答：这里究竟有什么东西，能让人和 Agent 对“做完了”形成相同的理解？我希望工作的组织中心是那件正在变清楚的作品。

一个 skill 可以先教会 Agent 这种行为：识别会改变结果的歧义，展示对照，把答案写回作品，保留未知事项。但如果要成为稳定的创作方式，还需要持续存在的共同对象，以及真正依据这个对象执行和验收的机制。否则，草图和实现仍然可能各自演化。

这些组成部分已经有不少前身。GitHub Spec Kit 的澄清流程会优先处理影响大、又不确定的问题，并把答案写回规格。Replit 对 Agent 4 的介绍则描述了同时容纳轻量原型和可交互预览的设计画布。这些工作已经覆盖了“先问清楚”和“先看见”的重要部分。[Spec Kit](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)；[Replit Agent 4](https://replit.com/blog/whats-changed-agent3-to-agent4)。

研究中也有相近方向。Socrates 通过合成多项选择问题来消除程序歧义，让用户在高层行为之间选择，并把选项与程序的形式化性质关联起来。这与“用可判断的行为帮助人表达意图”非常接近。[Choose, Don't Label，2026](https://arxiv.org/abs/2604.08792)。这些前身使我不愿轻易声称这里的每个部件都是新的。

我想继续追问的是，把这些部件组织成一种连续的创作过程后，能否让人更早获得充分理解，并合理地把注意力移走？如果预览、决策、实现和验收使用同一份持续更新的作品描述，那么聊天记录之外就有了一个真正承接意图的地方。这仍然是需要验证的设计假设。

验证时，不能只数 Agent 少问了几个问题，也不能只看用户多久点了确认。需要把前期构思、等待中的检查、后期审核和返工一起算进人的投入。还要检查，人能否解释预期结果，在不同情况下预判作品的行为，以及最终质量是否保持。一个漂亮预览也可能只让人更早产生错误的信心。

合理的比较对象，应当包括已经会澄清、会写计划、也会生成原型的系统。只有在相近模型和资源条件下，人的总投入下降、理解没有变差、结果仍然可靠，才有理由说这种组织方式带来了实际进步。对于很小的修改，快速实现可能已经足够；对于目标本身不断变化的探索，完整的交接也可能只能发生在一个阶段的末尾。

我期待的变化，是创作时人可以连续地想一件事。看到整个作品，提出判断，看见影响，再把理解推进一步。等到“对，做完就应该是这样”成为一个有依据的判断，Agent 才接过大部分实现工作。

那时，作品还需要时间。人已经可以去想下一件事了。
